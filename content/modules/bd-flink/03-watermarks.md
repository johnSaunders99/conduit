現在每五分鐘算一次付款筆數，但 P1 沒事件時整個看板不更新。浮水印（watermark）是作業對事件時間進度的聲明：「到這個時間點為止，正常應已看過。」它不是牆上的現在時間，也不是保證再也沒有更舊事件。窗口看到指標越過結束邊界，才能依規則收尾；如果先於浮水印到的是一筆舊事件，仍有機會被算入。晚於浮水印才收到同樣的舊事件，就要按遲到政策處理。這正是先選好[〈事件時間與處理時間〉](#/lesson/bd-flink-02)的業務時鐘，再決定願意等多長。

![兩路合併進度先取較慢的 12:03；只有 B 標記閒置後，才可沿用 A 的 12:08。](assets/bd-flink-watermarks.svg)

## 在兩條輸入上手算

假設 A 最新聲明 12:08，B 最新聲明 12:03。這裡數字已是浮水印，不是最大事件時間。作業合併活躍輸入取最小值 12:03；不能用 A 的 12:08 當全體進度。屬於 `[12:00,12:05)` 的窗口未越過結束邊界。B 長期無消息，若來源支援閒置（idleness）偵測，判它暫不參與合併後，A 就能把進度推到 12:08。B 重新出現且帶著 12:06，不會把已經合併的進度拉回去。實際等待、跳過、分流或重算，要看用的 API 和窗口型態，不是設定閒置後一律可補回。

在 Flink SQL，時間屬性的定義可用「依事件時間減固定延遲」產生保守進度。將容忍從 2 分鐘放到 20 分鐘，遲到數字可能降低，但準時客戶等待窗口更久，還要多留狀態。來源太安靜可設閒置期限，但先分清它是真的沒事件，還是上游故障、輪詢慢或被下游堵住。如果只是堵住，一排除它就可能讓窗口太早出結果。排查順序是逐路看最後收到時間、各分區浮水印，再看下游忙碌或等待，而不是將整條流的 `now` 拿來補。

## 給遲到事件一個去處

用 `flink-watermarks.md` 記下 B 恢復時那筆 12:06，並回答：如果付款看板已對外結算，是否能更正？可以另存原始接收日誌供離線對帳，或在 DataStream 以支援的側輸出（side output）送到獨立結果端。側輸出就是把事件送到主結果以外的管道；不能假設所有 SQL 窗口都有同樣的介面。交付時一併記「晚到總件數和待補窗口」，讓沒有出現在看板的付款仍可追索。

作業有多個來源運算子時，不只看單一 Kafka 分區。各段合併後的浮水印可能繼續被其他輸入拖住；量測點要標明在來源、合併後或窗口前。另外先用正常流量估閒置間隔，別因某條路每隔十分鐘才有一筆，就把正常沉默算成異常。

## 常見錯誤

- 使用最高浮水印 → 把慢路的事件誤判遲到 → 先取活躍輸入最小值。
- 閒置一恢復就假設所有舊事件可回填 → 合併時間不倒退 → 寫明晚到保存與修正策略。
- 盲調大延遲容忍 → 可能犧牲新鮮度 → 同量遲到率、出數時間與記憶體。
