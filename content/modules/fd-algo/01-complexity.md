## 先數動作，再看秒數

訂單檔今天有 8 筆，明天有 16 筆。掃一次加總與拿每對訂單互相比對，在小檔上都像是立刻完成，但數量再增加，兩種做法就不再相近。用 `n` 表示輸入筆數，選一個能計數的操作（例如比一次編號），再看操作次數隨 `n` 怎麼長。這是分析時間複雜度（time complexity）的入口；不需要先知道機器每秒能比較幾次。

大 O 記號（Big O notation）描述成長的上界。這裡用最有代表性的階來比較：固定步數是 `O(1)`，反覆減半是 `O(log n)`，逐筆掃是 `O(n)`，一般比較排序常見 `O(n log n)`，每對都比則是 `O(n²)`。掃兩遍做 `2n` 次仍是線性；兩層迴圈也不必然是平方，要看內層究竟執行幾次。一段始終只看前 10 筆的內層，不會因整份檔案變大就多看一筆。

## 用訂單位置數出差別

在 `C:\dev\conduit-lab\algorithms` 建立 `growth.py`，於該資料夾執行 `py growth.py`。每列依次印筆數、掃描步數、成對步數。

```python
def count_pairs(n):
    checks = 0
    for left in range(n):
        for right in range(left + 1, n):
            checks += 1
    return checks

for n in (4, 8, 16, 32):
    print(n, n, count_pairs(n))

assert count_pairs(8) == 28
```

固定左邊一筆，只和它右邊比，可以省掉自己與自己比、以及反向重算。8 筆時加的是 7、6、一路到 0；16 筆時變成 120 次。比值一開始不是 4，但公式 `n(n-1)/2` 中平方項會逐漸支配成長。如果只要找第一個重複，頭兩筆同號就能早停；若要求輸出所有配對，遇到第一對也不能停止，輸出本身甚至就可能有平方筆。反過來，找不到重複的輸入很適合拿來驗證早停程式是否只能靠運氣變快。

## 記憶體另外算

空間複雜度（space complexity）要先交代計算範圍。額外空間不重算既有輸入；固定數量的計數器是常數個位置，另建一份完整副本則多用線性空間。若有一張輸出表，要說清楚是否把它另計。〈[雜湊與集合](#/lesson/fd-algo-03)〉會用集合換掉成對走訪。集合最多存多少，比光說用了集合更有用。

帶到實作時先寫出上限，再決定要量什麼。若程式反覆開 CSV，耗時不只由比較決定；把讀檔和比對分開看。固定住檔案內容、環境與量法，才適合用秒數比較兩個版本。這堂只數次數，不宣稱量過實際工作負載。面試時也可以先講「如果每筆比較視為固定成本」，再報出成長率；若編號長度不固定，把這個假設寫進答案。

### 用小輸入驗證最壞情況

試把事件序列排成頭兩筆同號、只有最後一對同號、全部不同。三者的輸入大小相同，若程式遇重送就停，工作量仍不同。完整配對的版本則三次比較量一樣。寫下是哪種任務，否則連最好和最壞都沒法比較。

## 常見錯誤

- 測到的小檔耗時相同 → 量測噪音可能蓋過差異 → 先數操作，再用不同規模量測。
- 看見兩層就報平方 → 內層範圍可能固定 → 寫出每輪次數再相加。
- 說用了陣列所以空間是線性 → 混淆輸入與新配置 → 分開列出輸入、輔助結構和輸出。
