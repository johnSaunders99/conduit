## 先給讀者一件能確認的事

作品集（portfolio）不是把學過的工具堆出來。一位營運讀者想核對昨天報表；一位工程讀者要找出兩次重跑是否同結果。選一位為主要讀者，然後在第一屏放最短路徑：這份輸出回答什麼問題、如何驗一次、你負責哪段。小作品可以是「把營運收到的一份訂單 CSV 轉成一列日報，辨認重送，並核對已付金額」。先不要承諾多天、跨時區退款或正式上線。

粒度（grain）指一列代表什麼。原始檔一列是一筆送達記錄，所以同一張訂單可以出現兩次；中間的唯一訂單集合一個 ID 一筆；最終日報一列是一個營業日，這裡用檔名以外的明確日期參數表示。不宣稱腳本能依時間切日；上游要先提供單日的檔案。只計狀態為已付款的唯一訂單金額，取消單仍在唯一訂單集合，但不進付款金額。

## 首頁放足夠手算的輸入

假設虛構訂單 O1 已付 120 元、O2 已付 80 元且送到兩次、O3 取消 70 元、O4 已付 50 元。先核對原始 5 筆去重後剩 4 張，已付為 3 張、250 元。只有解析後的 ID、狀態與金額都相同才當重送；同一 ID 卻有不同金額或狀態時，本作品拒絕這批而非猜新舊。這一反例能讓工程讀者看到你的邊界，又能讓營運知道金額是怎麼算出來。〈[可重現的 README](#/lesson/cr-portfolio-02)〉會用這筆數據做出可跑版本。

用一句「我負責規則定義、Python 轉換與核對，目前只驗單日虛構輸入」分開個人貢獻與作品邊界。如果作品是合作，先標自己的部分、再寫與別人的介面；不要把整個團隊成果當成個人成果。沒有真實數據也可以拿到回饋：只使用虛構數據，留住會讓原本的作法失敗的形狀，不公開公司畫面、來源路徑或真實識別碼。

### 給不同讀者一條可走的線

營運讀者先看日報和付款規則，不必先打開程式；工程讀者先找原始樣本與重跑方式，再進到同 ID 金額衝突的例子。兩條線最後都要回到同一個結果。你可以在首頁先寫「可先手算，再跑一次」，不要把完整操作手冊和所有設計選項塞在第一段。實際上如果還沒寫完腳本，只列規劃中的入口，不要留下無法開啟的假連結。

若改做實時職作品，範圍可以從單日彙總改為一段可重播的事件與明確遲到條件；若改做平台職，可以從一個失敗分區的診斷與恢復入手。重點不在複製本例的表，而在每種作品都有一個小到可以親手驗、又真的能回答職務問題的交付。

## 常見錯誤

- 首頁只列品牌 → 讀者不知道可以驗什麼 → 先寫輸出與一條核對算式。
- 把重送算成兩張訂單 → 原始列和唯一 ID 不是同一粒度 → 為兩層各寫一句。
- 用「能上線」替代明確驗證 → 沒有測過正式環境 → 將測試邊界留在結果旁邊。
