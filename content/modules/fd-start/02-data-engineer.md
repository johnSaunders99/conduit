## 一份日報不是從報表開始的

茶舖營運想知道：「昨天哪個時段退款最多？」付款和退款記在業務數據庫（operational database）；用戶在 App 看商品、加購物車，則寫成埋點日誌（event logs）。這兩種來源回答不同問題：付款能證明交易，點了付款按鈕不一定代表交易完成。開工前先跟營運確認退款是算退款當天，還是回扣原訂單日。只要口徑不同，即使兩條查詢都沒寫錯，日報也會不同。

數據開發工程師（data engineer，台灣常見職稱是資料工程師）讓這些紀錄能穩定地送到使用者手上。工作不只寫 SQL，還包括依約交付、發現錯帳，以及出問題時找出哪一段可以安全重跑。

## 跟一筆退款走過數倉

1. **採集與同步（ingestion and synchronization）。** 從業務系統讀付款與退款，從 App 收埋點。保留來源識別碼、事件時間與到達時間，就算晚到或重送也能追查。把數據複製到分析用環境，避免主管每次開報表都去查收銀系統。
2. **原始層（ODS）與明細層（DWD）。** ODS 留下收到的原始紀錄，供重跑和追查；DWD 統一格式，認出重送，讓一列代表一筆有效退款。核對同一退款編號是否重複，不因兩筆退款金額相同就合併。
3. **共用維度（DIM）、彙總層（DWS）與應用層（ADS）。** DIM 提供統一的商品、門市或日期定義，不是每筆退款都要經過的下一站。DWS 可彙總成「每家店、每小時退款多少」，ADS 則依營運需要準備日報或告警用表。分層名稱因公司而異；重點是能說明每張表給誰用、每列代表什麼。
4. **數據供應（serving）。** 日報和商業智慧（BI）可共用已核對的指標。推薦可能需要用戶最近的商品互動，AI 應用可能需要可追溯的文件和權限；它們不必都讀同一張 ADS 表，也不該無限制取得原始數據。

## 四種工作，交付物不一樣

| 工作方向 | 常交付什麼 | 先學哪裡 |
|---|---|---|
| 離線數倉 | 每天能準時更新、退款可對帳、能補跑的明細與日報 | [SQL 與維度建模](#/module/sq-model)，再學[排程](#/module/bd-orch) |
| 實時數據 | 幾秒或幾分鐘更新的交易統計，晚到及重送有處理規則 | SQL 窗口觀念，加上大數據與管道的 [Kafka](#/module/bd-kafka) 和 [Flink](#/module/bd-flink) |
| 數據平台 | 讓很多團隊共用的採集、調度、運算和監控；故障能定位 | 共同基礎與[分散式運算](#/module/bd-distrib)，依職缺加 [Java](#/module/fd-java) |
| 雲端與分析工程 | 雲端整合、可測試的指標模型、交付成本與可讀文件 | SQL 與建模，加上雲端與現代數據棧的 [dbt](#/module/cl-dbt) |

表格是按主要交付物分類，不是公司固定分組。小團隊可能由同一人維護排程、寫模型並對帳。無論選哪一支，共同基礎用來做出可重跑的程式，求職實戰則幫你把作品中的取捨說清楚。

## 一週可能這樣過

週一和營運對齊退款日期與分母。週二開發 SQL，先造「同額兩筆、其中一筆重送」的案例；週三把作業排在上游完成後執行，先在測試環境補跑一天。某晚凌晨 2 點任務失敗，隔天接到通知先查來源檔是否到齊，再看是哪一步中斷；不確定這次寫到哪裡，就不能盲目重跑。週五即使排程顯示成功，數據質量告警仍可能指出某店退款突然全為 0。工程師要查門市是否歇業、採集是否漏店，或 SQL 是否過濾錯誤；不是「任務跑完」就算交付。

## 常見錯誤

- **兩份日報差一天** → 使用了不同日期口徑 → 先標明退款依哪個日期歸屬，再比較金額。
- **明細表突然多一筆** → 把同一識別碼的重送當成新退款 → 回到 ODS 對照來源鍵，再修 DWD 規則。
- **排程成功但看板是空的** → 成功只表示程式執行完，沒有保證輸入完整 → 核對到達時間、列數和一筆已知退款。

## 小結：先回答這張表給誰用

拿一筆退款，說出它從哪裡開始、哪一層會去重、哪張表交給誰。如果一開始就被問到凌晨失敗怎麼辦，先說你會去哪裡找證據。今天不用背縮寫；要能沿著圖指出，錯誤發生在哪兩步之間。
