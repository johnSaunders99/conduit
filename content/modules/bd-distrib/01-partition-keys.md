## 先決定哪些數據要碰面

茶舖把門市訂單分給 3 個工作單位，想算出每個會員買了幾次。一張訂單是一列，會員編號是鍵（key）：它回答「哪些列屬於同一組」。分區（partition）是邏輯上的一份工作，不等同一台電腦。一台可以同時處理好幾份；不同時刻也可能由不同電腦接手同一份。今天只看一件事：在規則不變時，同一個鍵如何走向同一個接收方。

若把檔案平分成三段，人人收到的列數或許差不多，但會員 7 可能在每段都有訂單。單看任一段的結果都不完整。反過來，把會員鍵映射到分區，同鍵會相遇，計數便可在接收端完成。兩種切法不是誰比較先進：前者適合逐列清洗，後者適合讓同鍵聚合（aggregation），也就是把同組多列合成一個結果。

## 用餘數當分區號

這次用 `key % n` 當簡單映射：`%` 取整數除法的餘數，`n` 是分區數，分區號從 0 起算。實務可先把字串鍵轉成固定整數，稱為雜湊（hash）；需要跨程序保持映射時，不能把 Python 字串的內建 `hash()` 當跨次執行的固定值。選鍵時也要先說清楚數據粒度：若目標是按店舖計算，會員鍵未必是最終合流的鍵。

鍵不重複不代表分區不碰撞。`4 % 3` 與 `7 % 3` 都為 1，兩個不同鍵互不混算，只是共用接收方。反之，一個熱鍵（hot key）連續來 4 筆，4 筆一定送到同一區。真正限制整批結束時間的常是最重的一區，不是總列數除以分區數。試想分區 0 做完後，能不能在**不改計算方式**的情況下替分區 1 算一半鍵 7？不能；那樣就失去單一分區擁有完整小計的前提。

## 把分派存成負載表

Windows 的 PowerShell 在 `C:\dev\conduit-lab` 下新建 `bd-distrib` 資料夾，將下列程式存為 `route.py`，進入該資料夾執行 `py route.py`。這是單機路由模型，不安裝 Hadoop；練習預留 0.25 GB RAM。
```python
from collections import Counter

keys = [2, 3, 4, 6, 7, 7, 7, 7]
loads = Counter(key % 3 for key in keys)
for part in range(3):
    print(part, loads[part])
assert sum(loads.values()) == len(keys)
```

輸出的第一欄是分區號，第二欄是列數。確認 `2、5、1` 後，把清單末尾兩個 `7` 拿掉，再算一次。若兩次最大分區都為 1，其原因不是 1 號電腦慢，而是 1 號收到了多個同鍵紀錄。再用紙筆算 `7 % 4`，體會更改分區數也可能改變目的地。記錄分區數是 3 還是 4，否則下次沒辦法重現路由。如何讓熱鍵分攤又保留正確結果，見[〈Shuffle 與傾斜〉](#/lesson/bd-distrib-06)。

### 先寫出不可拆的條件

若客服要查單一會員的完整購買歷史，就優先問上游能不能提供穩定會員鍵；若新舊系統發的編號能相撞，要把來源也納入鍵。否則即使分派完全符合規則，也會把兩個人合成一組。

## 常見錯誤

- 每次重送到不同區 → 把暫時空閒當分派規則 → 先固定同鍵映射。
- 同一區得到兩個不同鍵 → 這是分區碰撞，不是鍵相同 → 區內仍以原鍵分組。
- 分區數加倍，最重區仍慢 → 熱鍵未被拆開 → 先用鍵頻率證明瓶頸，再選拆鍵或局部聚合。
